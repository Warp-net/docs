# Локальное хранилище {#local-storage}

Каждый member-узел хранит данные своего владельца в зашифрованной базе данных на собственном диске владельца: посты, профиль, подписки, чаты, медиа, настройки и долю узла в реплицируемых хранилищах. На этой странице описано, где лежит эта база данных, как она шифруется, как организованы ключи, что удаляется автоматически, как работает очередь исходящих (outbox) для пиров не в сети и база данных echo-узла в памяти. Первые разделы — для пользователей и операторов, остальное — для разработчиков.

## Обзор {#overview}

| Вопрос | Ответ |
|---|---|
| Движок | [BadgerDB](https://github.com/dgraph-io/badger) v4, встраиваемое хранилище «ключ — значение» |
| Шифрование | Всегда включено, ключ выводится из вашего логина и пароля |
| Расположение | `~/.warpdata` в Linux и macOS; `%LOCALAPPDATA%\warpdata` в Windows |
| Отдельная база данных | Для каждой сети (`warpnet`, `testnet`) и каждого имени каталога базы данных |
| Кто хранит данные на диске | Member-узлы: десктопное приложение и удаленный узел |
| Кто держит данные только в памяти | Echo-узел, relay-узлы и модераторы |
| Команда резервного копирования или экспорта | Нет (см. [Резервное копирование](#backup-and-export)) |

## Где хранятся данные {#where-data-lives}

Каталог приложения зависит от операционной системы ([`config/config.go`](https://github.com/Warp-net/warpnet/blob/main/config/config.go)):

| ОС | Каталог приложения |
|---|---|
| Linux, macOS | `$HOME/.warpdata` |
| Linux, пакет Snap | `~/snap/warpnet/current/.warpdata` (Snap подставляет в `$HOME` собственный каталог данных snap-пакета) |
| Windows | `%LOCALAPPDATA%\warpdata` (узел завершает работу, если переменная не задана) |

Внутри него путь к базе данных строится из сети и имени каталога базы данных, а сама база добавляет папку `v0`:

```text
<application dir>/<network>/<database dir>/v0
```

Со значениями по умолчанию (`--node.network=warpnet`, `--database.dir=storage`) это `~/.warpdata/warpnet/storage/v0`. Типичное дерево:

```text
~/.warpdata/
├── fontconfig.conf        Linux desktop app outside Snap (font settings for the window)
├── warpnet/               main network
│   ├── ws-noise.key       remote node only
│   └── storage/
│       └── v0/
│           ├── run.lock   written after the first successful login
│           └── ...        BadgerDB files
└── testnet/
    └── storage/
        └── v0/
```

| Настройка | Флаг | Переменная окружения | По умолчанию |
|---|---|---|---|
| Сеть | `--node.network` | `NODE_NETWORK` | `warpnet` (`mainnet` принимается как псевдоним) |
| Имя каталога базы данных | `--database.dir` | `DATABASE_DIR` | `storage` |

Файла конфигурации нет: настройки берутся из флагов и переменных окружения. Запуск в testnet или с другим `--database.dir` дает полностью отдельную базу данных.

`ws-noise.key` — статический ключ удаленного узла для зашифрованного канала панели. Это обычный файл, доступный для чтения только владельцу (режим `0600`), и он лежит вне зашифрованной базы данных.

В Docker-образах проекта узел работает от `root`, поэтому данные лежат в `/root/.warpdata`; смонтируйте туда том, чтобы данные сохранялись между перезапусками контейнера.

> **Внимание:** BadgerDB блокирует свой каталог, а десктопное приложение допускает только один запущенный экземпляр. Два узла не могут использовать один каталог базы данных.
{: .warning }

## Какие узлы что хранят {#which-nodes-store-what}

| Узел | База данных | Реплицируемые хранилища |
|---|---|---|
| Десктопное приложение (member) | Зашифрованная BadgerDB на диске | Статистика и рейтинг, внутри той же базы данных |
| Удаленный узел (member) | Зашифрованная BadgerDB на диске | Статистика и рейтинг, внутри той же базы данных |
| Echo-узел (member, тестовый бот) | Зашифрованная BadgerDB **в памяти** | Статистика и рейтинг, в памяти |
| Relay-узел | Нет BadgerDB; хранилища данных в памяти для peerstore и DHT | Только рейтинг, в памяти |
| Модератор | Нет BadgerDB; хранилища данных в памяти | Только рейтинг, в памяти |

Relay-узлы и модераторы теряют состояние при перезапуске и получают свое представление о рейтингах обратно от пиров, см. [Синхронизация](synchronization.md#startup-and-recovery).

## Шифрование при хранении {#encryption-at-rest}

База данных открывается только после входа, ключом, выведенным из ваших учетных данных ([`security/kdf.go`](https://github.com/Warp-net/warpnet/blob/main/security/kdf.go), [`security/aes.go`](https://github.com/Warp-net/warpnet/blob/main/security/aes.go)):

```text
salt = SHA-256("warpnet/kdf/v1/database-key" || 0x00 || login)
key  = Argon2id(password, salt, time=1, memory=64 MiB, threads=4, length=32 bytes)
```

- 32-байтный ключ передается BadgerDB как ключ шифрования и никогда не записывается на диск.
- BadgerDB шифрует свои файлы с помощью AES (32-байтный ключ означает AES-256) в режиме CTR. Данные шифруются внутренними ключами данных, которые сами защищены этим ключом и меняются каждые 10 дней (значение BadgerDB по умолчанию).
- При неверном логине или пароле база данных не открывается, и выводится сообщение «wrong username or password».
- Ключ базы данных зависит только от логина и пароля. Сети разделяются каталогами, а не ключом.
- Ключ идентичности вашего узла выводится отдельно — из логина, пароля **и** сети, со своей контекстной строкой. См. [Безопасность](security.md).

Восстановить пароль или сменить логин либо пароль нельзя. Если вы забудете любой из них, базу данных расшифровать не удастся. Вход с теми же логином и паролем на другой машине дает тот же ID узла, но сами данные остаются только в старой базе.

## Настройки движка {#engine-settings}

Из [`database/local-store/db.go`](https://github.com/Warp-net/warpnet/blob/main/database/local-store/db.go):

| Настройка | На диске | В памяти (echo-узел) |
|---|---|---|
| Синхронная запись | выкл. | выкл. |
| Сжатие | ZSTD | Snappy (значение BadgerDB по умолчанию) |
| Кэш индекса | 256 MiB | 256 MiB |
| Кэш блоков | 512 MiB | 512 MiB |
| Компакторы | 4 | 2 |
| Сборка мусора в value log | при входе, затем каждый час | не выполняется |
| Наблюдатель за каталогом | каждую секунду | не выполняется |

С выключенной синхронной записью BadgerDB не сбрасывает каждую запись на диск принудительно. При отключении питания или сбое ОС последние записи могут потеряться.

## Жизненный цикл {#lifecycle}

1. **Запуск.** Узел подготавливает базу данных, но пока не открывает ее. Он проверяет, есть ли `run.lock` в папке базы данных; если нет, это первый запуск.
2. **Вход.** Выводится ключ, и база данных открывается. При первом открытии записывается `run.lock`.
3. **Работа.** Сборка мусора в value log выполняется один раз при открытии базы, а затем каждый час и повторяется, пока BadgerDB находит, что переписать (порог discard ratio 0.5, пауза в одну секунду между проходами). Каждую секунду узел проверяет, что `run.lock` на месте; если папку очистили во время работы узла, узел аварийно завершается с ошибкой `database: folder was emptied`, а не продолжает работу с пустой базой.
4. **Выход или остановка.** База данных закрывается. Повторный вход снова открывает ее.

## Структура ключей {#key-layout}

BadgerDB — плоское хранилище «ключ — значение», отсортированное по байтам. Warpnet строит ключи, похожие на пути, с помощью построителя префиксов ([`prefix-tree.go`](https://github.com/Warp-net/warpnet/blob/main/database/local-store/prefix-tree.go)):

```text
/<NAMESPACE>[/<SUBPREFIX>...]/<root id>/<range>/<id>[/<id>...]
```

- **Пространство имен:** в верхнем регистре, одно или несколько на репозиторий, например `/TWEETS`.
- **Корневой ID:** то, по чему сгруппированы элементы: ID пользователя, ID поста (ответы, счетчики), ID узла-получателя (outbox) или корень сети (пользователи).
- **Диапазон:** литерал `fixed`, литерал `none` или число.
- **ID:** ULID, хеши или peer ID.

### Фиксированные и сортируемые ключи {#fixed-and-sortable-keys}

Большинство сущностей, которые выводятся списками, записываются дважды. Например, пост:

```text
/TWEETS/{userId}/fixed/{tweetId}                 -> the sortable key below
/TWEETS/{userId}/9223370241376375807/{tweetId}   -> the post as JSON
```

(Число — это обратная метка времени поста, опубликованного в 00:00 UTC 24 ноября 2026 года.)

**Фиксированный** ключ находит элемент по ID. **Сортируемый** ключ содержит обратную метку времени `MaxInt64 - unixMillis`, дополненную нулями до 19 цифр, так что обычное сканирование по префиксу возвращает сначала самые новые элементы. Сканирование отказывается работать с префиксом, содержащим `fixed`, и пропускает любые встреченные ключи `fixed`, поэтому списки никогда не возвращают элемент дважды. Ответ хранится как пост под ID родительского поста, а не под ID пользователя.

### Пользователи {#users}

Записи пользователей сгруппированы по сетям ([`database/user-repo.go`](https://github.com/Warp-net/warpnet/blob/main/database/user-repo.go)):

```text
/USERS/USER/None/fixed/{userId}        -> the sortable key below
/USERS/USER/{root}/{rtt}/{userId}      -> the profile as JSON
/USERS/NODE/{nodeId}                   -> the sortable key of the user on that node
```

- `{root}` — это `warpnet/`, `mastodon/`, `threads/` или `nostr/`: название сети пользователя с завершающей косой чертой, чтобы сканирование одной сети никогда не заходило в другую, название которой начинается так же. Запись хранится, например, как `/USERS/USER/warpnet//125000/{userId}`. Пользователь без метки сети или из любой другой сети хранится под `None`.
- `{rtt}` — время приема-передачи до узла пользователя в миллисекундах на момент записи; 125000, если оно не измерялось. Собственная запись владельца использует наибольшее 64-битное значение.
- Когда обновление меняет сеть пользователя, запись переносится в новый корень в той же транзакции.
- ID пользователя остается привязанным к первому сохраненному для него ID узла; обновление, указывающее другой узел, отвергается.
- Рекомендации Who to follow сначала читают корень запрошенной сети, затем `None`, пропуская пользователей не в сети и пользователей других сетей, и останавливаются после 5000 записей на запрос.

### Списки {#listing}

Сканирование по префиксу разбито на страницы. Страница по умолчанию содержит 20 элементов, максимум — 1000. Сканирование возвращает непрозрачный курсор для следующей страницы или литерал `end`, когда префикс исчерпан.

## Пространства имен {#namespaces}

| `/FOLLOW` | Подписки, подписчики, их счетчики |
| `/BLOCKS`, `/MUTES` | Пользователи, которых владелец заблокировал или скрыл |

| `/BOOKMARKS` | Посты в закладках |
| `/NOTIFICATIONS` | Уведомления |
| `/CHATS`, `/MESSAGES` | Личные чаты и их сообщения |
| `/MEDIA` | Изображения и видео |
| `/CHATMEDIA` | Вложения чатов |
| `/SPONSOREDMEDIA` | Помеченные копии платных медиа для каждого покупателя и хеши изображений платных постов |
| `/ORDERS`, `/ORDERPAYERS` | Заказы на платные посты и узел покупателя, привязанный к каждому адресу плательщика |

| `/SETTINGS` | Настройки уведомлений и настройки узла (шлюз, лимиты частоты запросов, спонсорский контент, сеть, кошелек) |
| `/ALIASES` | Подключенные мобильные устройства |
| `/OUTBOX` | Запросы на запись, ожидающие пира не в сети (см. ниже) |

Репозитории находятся в [`database/`](https://github.com/Warp-net/warpnet/tree/main/database), по одному файлу на область данных.

## Что удаляется само {#what-expires-on-its-own}

Некоторые записи сохраняются со сроком жизни (TTL), и BadgerDB удаляет их автоматически:

| Данные | Срок хранения |
|---|---|
| Уведомления | 24 часа |
| Подключенные устройства | 72 часа, срок обновляется при каждом повторном сопряжении устройства; при запуске узла все сопряжения отзываются |
| Кэшированные изображения и видео других пользователей | 7 дней |
| Посты, загруженные с другого узла при просмотре его профиля | 30 дней |
| Сообщения в outbox | 30 дней |

Ваш собственный контент (посты, чаты, лента, настройки, закладки, подписки) срока истечения не имеет. Узел заблокированного пользователя остается в черном списке пиров, пока владелец не разблокирует пользователя.

Реплицируемые хранилища очищаются отдельно: счетчики постов старше 30 дней и записи рейтинга с истекшим сроком хранения удаляются день за днем, см. [Синхронизация](synchronization.md#day-dags).

## Очередь исходящих (outbox) {#outbox}

Когда member-узел отправляет запрос на запись другому узлу (подписку, ответ на чужой пост, реакцию, сообщение в чате и любой другой маршрут, кроме чтения), запрос сначала сохраняется в outbox, а затем отправляется ([`core/stream/outbox.go`](https://github.com/Warp-net/warpnet/blob/main/core/stream/outbox.go), [`database/outbox-repo.go`](https://github.com/Warp-net/warpnet/blob/main/database/outbox-repo.go)).

```text
/OUTBOX/{destinationNodeId}/{messageId}   -> route, body, timestamp (JSON)
```

- Если пир подтверждает получение, элемент очереди удаляется.
- Если пир не в сети или отправка не удалась, элемент остается, а вызывающей стороне сообщается, что запрос поставлен в очередь.
- Запросы из очереди отправляются повторно, когда пир подключается, каждые 5 минут и при запуске узла.
- Если пир отвечает ошибкой ограничения частоты запросов, этот маршрут остается в очереди до следующей попытки.
- Один и тот же запрос, поставленный в очередь для одного пира дважды подряд, сохраняется один раз.
- Запросы на чтение никогда не ставятся в очередь.
- Элементы очереди истекают через 30 дней, если пир так и не вернулся.

## Медиа {#media}

Изображения и видео хранятся внутри BadgerDB как строки base64 под `/MEDIA/IMAGES/{userId}/{key}` и `/MEDIA/VIDEOS/{userId}/{key}`, где `key` — hex SHA-256 сохраненных данных. Поэтому одно и то же содержимое всегда получает один и тот же ключ. Ваши собственные медиа хранятся, пока вы их не удалите; медиа, загруженные у других пользователей, кэшируются на 7 дней. Вложения чатов используют `/CHATMEDIA` с той же структурой.

Отдельного файлового хранилища для медиа нет. Изображение другого пользователя загружается с его узла через поток при просмотре, проверяется и затем кэшируется локально.

## Резервное копирование и экспорт {#backup-and-export}

Команды экспорта, импорта или резервного копирования базы данных нет. Что есть:

- Каталог базы данных можно скопировать, пока узел **остановлен**. Копию можно открыть только с теми же логином и паролем.
- ID узла воспроизводим: те же логин, пароль и сеть дают тот же ID узла на любой машине. Новая пустая база данных при этом все равно начинает новый профиль с новым ID пользователя.
- Seed кошелька тоже не хранится в базе данных: он выводится из вашего ключа идентичности, сети и логина, поэтому те же учетные данные дают тот же кошелек.

Пошаговая инструкция для пользователей — на странице [Резервное копирование и восстановление](user-guide/backup-and-restore.md).

## База данных echo-узла в памяти {#in-memory-database-of-the-echo-node}

Тестовый echo-узел ([`cmd/node/member/echo-member.go`](https://github.com/Warp-net/warpnet/blob/main/cmd/node/member/echo-member.go)) открывает BadgerDB с `local_store.DefaultOptions().WithInMemory(true)`. В этом режиме:

- ничего не записывается на диск, и все теряется при выходе;
- `run.lock` не записывается, а сборка мусора и наблюдатель за каталогом не запускаются;
- шифрование все равно настраивается ключом, выведенным из фиксированных логина и пароля echo-узла.

Echo-узел открывает базу данных до входа, чтобы заполнить данные своего фиксированного владельца; открытие уже работающей базы ничего не делает, поэтому заполненные данные сохраняются.

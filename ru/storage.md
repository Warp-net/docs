# Локальное хранилище {#local-storage}

Каждый member-узел хранит данные своего владельца в зашифрованной базе данных на собственном диске владельца: посты, профиль, подписки, чаты, медиа, настройки и долю узла в реплицируемых хранилищах. На этой странице описано, где лежит эта база данных, как она шифруется, как организованы ключи, что удаляется автоматически, как работает очередь исходящих (outbox) для пиров не в сети и режим работы в памяти, который используют тестовые узлы. Первые разделы — для пользователей и операторов, остальное — для разработчиков.

## Обзор {#overview}

| Вопрос | Ответ |
|---|---|
| Движок | [BadgerDB](https://github.com/dgraph-io/badger) v4, встраиваемое хранилище «ключ — значение» |
| Шифрование | Всегда включено, ключ выводится из вашего имени пользователя и пароля |
| Расположение | `~/.warpdata` в Linux, macOS и Android; `%LOCALAPPDATA%\warpdata` в Windows |
| Отдельная база данных | Для каждой сети (`warpnet`, `testnet`) и каждого имени каталога базы данных |
| Кто хранит данные на диске | Member-узлы: десктопное приложение и удаленный узел |
| Кто держит данные только в памяти | Echo-узлы, relay-узлы и модераторы |
| Команда резервного копирования или экспорта | Нет (см. [Резервное копирование](#backup-and-export)) |

## Где хранятся данные {#where-data-lives}

Каталог приложения зависит от операционной системы ([`config/config.go`](https://github.com/Warp-net/warpnet/blob/main/config/config.go)):

| ОС | Каталог приложения |
|---|---|
| Linux, macOS, Android | `$HOME/.warpdata` |
| Windows | `%LOCALAPPDATA%\warpdata` (узел завершает работу, если переменная не задана) |
| Любая другая | Не поддерживается; узел завершает работу |

Внутри него путь к базе данных строится из трех частей, а сама база добавляет папку с версией схемы:

```text
<application dir>/<network>/<database dir>/v0
```

Со значениями по умолчанию (`--node.network=warpnet`, `--database.dir=storage`) это `~/.warpdata/warpnet/storage/v0`. Типичное дерево:

```text
~/.warpdata/
├── fontconfig.conf        Linux desktop app only (font settings for the window)
├── warpnet/               main network
│   ├── ws-noise.key       remote node only
│   └── storage/
│       └── v0/
│           ├── run.lock   written after the first successful login
│           └── ...        BadgerDB files
└── testnet/
    └── storage/
        └── v0/
```

| Настройка | Флаг | Переменная окружения | По умолчанию |
|---|---|---|---|
| Сеть | `--node.network` | `NODE_NETWORK` | `warpnet` (`mainnet` принимается как псевдоним) |
| Имя каталога базы данных | `--database.dir` | `DATABASE_DIR` | `storage` |

Файла конфигурации нет: настройки берутся из флагов и переменных окружения. Запуск в testnet или с другим `--database.dir` дает полностью отдельную базу данных. Так на одной машине можно запустить несколько узлов.

`ws-noise.key` — статический ключ удаленного узла для зашифрованного канала панели. Это обычный файл, доступный для чтения только владельцу (режим `0600`), и он лежит вне зашифрованной базы данных.

В Docker-развертываниях проекта узел работает от `root`, поэтому данные лежат в `/root/.warpdata`; смонтируйте туда том, чтобы данные сохранялись между перезапусками контейнера.

> **Внимание:** BadgerDB блокирует свой каталог, а десктопное приложение допускает только один запущенный экземпляр. Два узла не могут использовать один каталог базы данных.
{: .warning }

## Какие узлы что хранят {#which-nodes-store-what}

| Узел | База данных | Реплицируемые хранилища |
|---|---|---|
| Десктопное приложение (member) | Зашифрованная BadgerDB на диске | Статистика и рейтинг, внутри той же базы данных |
| Удаленный узел (member) | Зашифрованная BadgerDB на диске | Статистика и рейтинг, внутри той же базы данных |
| Echo-узел (member, тестовый бот) | BadgerDB **в памяти** | Статистика и рейтинг, в памяти |
| Relay-узел | Нет BadgerDB; хранилища данных в памяти для peerstore и DHT | Только рейтинг, в памяти |
| Модератор | Нет BadgerDB; хранилища данных в памяти | Только рейтинг, в памяти |

Relay-узлы и модераторы теряют состояние при перезапуске и получают свое представление о рейтингах обратно от пиров, см. [Синхронизация](synchronization.md#startup-and-recovery).

## Шифрование при хранении {#encryption-at-rest}

База данных открывается только после входа, ключом, выведенным из ваших учетных данных ([`security/kdf.go`](https://github.com/Warp-net/warpnet/blob/main/security/kdf.go), [`security/aes.go`](https://github.com/Warp-net/warpnet/blob/main/security/aes.go)):

```text
salt = SHA-256("warpnet/kdf/v1/database-key" || 0x00 || username)
key  = Argon2id(password, salt, time=1, memory=64 MiB, threads=4, length=32 bytes)
```

- 32-байтный ключ передается BadgerDB как ключ шифрования и никогда не записывается на диск.
- BadgerDB шифрует свои файлы с помощью AES (32-байтный ключ означает AES-256) в режиме CTR. Данные шифруются внутренними ключами данных, которые сами защищены этим ключом и по умолчанию меняются каждые 10 дней.
- При неверном имени пользователя или пароле база данных не открывается, и выводится сообщение «wrong username or password».
- Ключ базы данных зависит только от имени пользователя и пароля. Сети разделяются каталогами, а не ключом.
- Ключ идентичности вашего узла выводится отдельно — из имени пользователя, пароля **и** сети, со своей контекстной строкой. См. [Безопасность](security.md).

Восстановить или сменить пароль нельзя. Если вы забудете пароль, базу данных расшифровать не удастся. Поскольку идентичность выводится из тех же учетных данных, вход с ними на другой машине дает тот же ID узла, но сами данные остаются только в старой базе.

## Настройки движка {#engine-settings}

Из [`database/local-store/db.go`](https://github.com/Warp-net/warpnet/blob/main/database/local-store/db.go):

| Настройка | На диске | В памяти |
|---|---|---|
| Синхронная запись | выкл. | выкл. |
| Сжатие | ZSTD | нет |
| Кэш индекса | 256 MiB | 256 MiB |
| Кэш блоков | 512 MiB | 512 MiB |
| Компакторы | 4 | 2 |
| Сборка мусора в value log | при запуске, затем каждый час | не выполняется |
| Наблюдатель за каталогом | каждую секунду | не выполняется |

С выключенной синхронной записью BadgerDB не сбрасывает каждую запись на диск принудительно. При отключении питания или сбое ОС последние записи могут потеряться.

Последовательность BadgerDB под ключом `/SEQUENCE` выдает монотонно растущие числовые ID.

## Жизненный цикл {#lifecycle}

1. **Запуск.** Узел подготавливает базу данных, но пока не открывает ее. Он проверяет, есть ли `run.lock` в папке базы данных; если нет, это первый запуск.
2. **Вход.** Выводится ключ, и база данных открывается. При первом успешном входе записывается `run.lock`.
3. **Работа.** Сборка мусора в value log выполняется один раз при запуске, а затем каждый час и повторяется, пока BadgerDB не сообщит, что переписывать больше нечего. Каждую секунду узел проверяет, что `run.lock` на месте; если папку очистили во время работы узла, узел останавливается с ошибкой, а не продолжает работу с пустой базой.
4. **Выход или остановка.** База данных закрывается. Повторный вход снова открывает ее.

## Структура ключей {#key-layout}

BadgerDB — плоское хранилище «ключ — значение», отсортированное по байтам. Warpnet строит ключи, похожие на пути, с помощью построителя префиксов ([`prefix-tree.go`](https://github.com/Warp-net/warpnet/blob/main/database/local-store/prefix-tree.go)):

```text
/<NAMESPACE>[/<SUBPREFIX>...]/<root id>/<range>/<id>[/<id>...]
```

- **Пространство имен:** в верхнем регистре, по одному на репозиторий, например `/TWEETS`.
- **Корневой ID:** обычно ID пользователя-владельца.
- **Диапазон:** литерал `fixed`, литерал `none` или число.
- **ID:** ULID, хеши или peer ID.

### Фиксированные и сортируемые ключи {#fixed-and-sortable-keys}

Большинство сущностей, которые выводятся списками, записываются дважды. Например, пост:

```text
/TWEETS/{userId}/fixed/{tweetId}                 -> the sortable key below
/TWEETS/{userId}/9223370241376375807/{tweetId}   -> the post as JSON
```

(Число — это обратная метка времени поста, опубликованного в 00:00 UTC 24 ноября 2026 года.)

**Фиксированный** ключ находит элемент по ID. **Сортируемый** ключ содержит обратную метку времени `MaxInt64 - unixMillis`, дополненную нулями до 19 цифр, так что обычное сканирование по префиксу возвращает сначала самые новые элементы. Сканирование отказывается работать с префиксом, содержащим `fixed`, и пропускает любые встреченные ключи `fixed`, поэтому списки никогда не возвращают элемент дважды.

### Списки {#listing}

Сканирование по префиксу разбито на страницы. Страница по умолчанию содержит 20 элементов, максимум — 1000. Сканирование возвращает непрозрачный курсор для следующей страницы или литерал `end`, когда префикс исчерпан. Большие пакетные записи, которые не помещаются в одну транзакцию, фиксируются и продолжаются автоматически.

| `/ALIASES` | Подключенные мобильные устройства |

Репозитории находятся в [`database/`](https://github.com/Warp-net/warpnet/tree/main/database), по одному файлу на пространство имен.

## Что удаляется само {#what-expires-on-its-own}

Некоторые записи сохраняются со сроком жизни (TTL), и BadgerDB удаляет их автоматически:

| Данные | Срок хранения |
|---|---|
| Уведомления | 24 часа |
| Подключенные устройства | 72 часа |
| Кэшированные изображения и видео других пользователей | 7 дней |
| Посты, загруженные с другого узла при просмотре его профиля | 30 дней |
| Сообщения в outbox | 30 дней |
| Записи черного списка пиров | 1 час, 24 часа, 7 дней, затем навсегда — срок растет при каждом повторе |

Ваш собственный контент (посты, чаты, лента, настройки, закладки, подписки) срока истечения не имеет.

Реплицируемые хранилища очищаются отдельно: счетчики постов старше 30 дней и записи рейтинга с истекшим сроком хранения удаляются день за днем, см. [Синхронизация](synchronization.md#day-dags).

## Очередь исходящих (outbox) {#outbox}

Когда member-узел отправляет запрос на запись другому узлу (подписку, ответ в чужой ветке и другие запросы, кроме чтения), запрос сначала сохраняется в outbox, а затем отправляется ([`core/stream/outbox.go`](https://github.com/Warp-net/warpnet/blob/main/core/stream/outbox.go), [`database/outbox-repo.go`](https://github.com/Warp-net/warpnet/blob/main/database/outbox-repo.go)).

```text
/OUTBOX/{destinationNodeId}/{messageId}   -> route, body, timestamp (JSON)
```

- Если пир подтверждает получение, элемент очереди удаляется.
- Если пир не в сети или отправка не удалась, элемент остается, а вызывающей стороне сообщается, что запрос поставлен в очередь.
- Запросы из очереди отправляются повторно, когда пир подключается, каждые 5 минут и при запуске узла.
- Если пир отвечает ошибкой ограничения частоты запросов, этот маршрут остается в очереди до следующей попытки.
- Один и тот же запрос, поставленный в очередь для одного пира дважды подряд, сохраняется один раз.
- Запросы на чтение никогда не ставятся в очередь.
- Элементы очереди истекают через 30 дней, если пир так и не вернулся.

## Медиа {#media}

Изображения и видео хранятся внутри BadgerDB как строки base64 под `/MEDIA/IMAGES/{userId}/{key}` и `/MEDIA/VIDEOS/{userId}/{key}`, где `key` — hex SHA-256 сохраненных данных. Поэтому одно и то же содержимое всегда получает один и тот же ключ. Ваши собственные медиа хранятся, пока вы их не удалите; медиа, загруженные у других пользователей, кэшируются на 7 дней. Вложения чатов используют `/CHATMEDIA` с той же структурой.

Отдельного файлового хранилища для медиа нет. Изображение другого пользователя загружается с его узла через поток при просмотре, проверяется и затем кэшируется локально.

## Версии и миграция {#versions-and-migration}

- Папка `v0` защищает версию схемы. При будущем несовместимом изменении узел перейдет в новую папку и начнет с чистой базы данных, а не будет мигрировать данные на месте. Сегодня существует только `v0`.
- Внутри `v0` изменения обрабатываются сменой префиксов. Когда реплицируемые хранилища перешли на DAG по дням, они получили новые префиксы (`/STATS/DAYS`, `/RATING/DAYS`); старые данные под `/CRDT` и `/RATING` остаются на диске и не читаются.

## Резервное копирование и экспорт {#backup-and-export}

Команды экспорта, импорта или резервного копирования базы данных нет. Что есть:

- Каталог базы данных можно скопировать, пока узел **остановлен**. Копию можно открыть только с теми же именем пользователя и паролем.
- Идентичность воспроизводима: те же имя пользователя, пароль и сеть дают тот же ID узла на любой машине, даже без старых данных.
- Seed кошелька тоже не хранится в базе данных: он выводится из вашего ключа идентичности, сети и логина, поэтому те же учетные данные дают тот же кошелек.

Пошаговая инструкция для пользователей — на странице [Резервное копирование и восстановление](user-guide/backup-and-restore.md).

## Режим в памяти {#in-memory-mode}

`DefaultOptions().WithInMemory(true)` запускает BadgerDB полностью в памяти. Его использует тестовый echo-узел ([`cmd/node/member/echo-member.go`](https://github.com/Warp-net/warpnet/blob/main/cmd/node/member/echo-member.go)). В этом режиме:

- ничего не записывается на диск, и все теряется при выходе;
- `run.lock` не записывается, а сборка мусора и наблюдатель за каталогом не запускаются;
- шифрование все равно настраивается выведенным ключом, как и на диске.

Echo-узел открывает базу данных до входа, чтобы заполнить данные своего фиксированного владельца; повторное открытие уже работающей базы ничего не делает, поэтому заполненные данные не теряются.

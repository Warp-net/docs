# Сеть и транспорт {#network-and-transport}

Эта страница описывает сетевую сторону Warpnet: какие соединения устанавливают узел и мобильные приложения, какие слои оборачивают каждое соединение, как узлы за NAT находят друг друга и что наблюдатель на пути трафика может и не может увидеть. Она написана для пользователей, которые хотят знать, что покидает их компьютер, для сборщиков пакетов и для ревьюеров.

## Роли узлов в сети {#node-roles-on-the-network}

| Роль | Где работает | В сети |
|---|---|---|
| Member-узел | ваш компьютер или сервер | ваш узел: хранит ваши данные, обслуживает интерфейс десктопного приложения, браузерную панель (вариант remote) и подключенные телефоны |
| Relay-узел | хост с публичным IP | работает без интерфейса, все держит в памяти, объявляет себя публично доступным; запускает DHT, gossip и сервис circuit relay v2 |
| Узел-модератор | сервер | оценивает контент, на который поступили жалобы; см. [Модерация](moderation.md) |
| Мобильное приложение | телефон на Android или iOS | клиент member-узла, с которым оно сопряжено; только устанавливает исходящие соединения |

«Bootstrap-узел» — это не роль. Это любой адрес из списка bootstrap-узлов узла: первые пиры, к которым узел подключается, начальные узлы его DHT и единственные relay-узлы, на которых он резервирует слоты, если находится за NAT. Встроенный список ([`config/config.go`](https://github.com/Warp-net/warpnet/blob/main/config/config.go)) — это три relay-узла, которые проект держит на одном хосте, `207.154.221.44` (IPv4 и IPv6; TCP-порты с 4001 по 4003 в `warpnet`, 4011, 4022 и 4033 в `testnet`). Как выбирается и используется этот список: [Обнаружение](discovery.md#bootstrap-nodes). Как его заменить: [Как обойтись без хостов проекта](#keeping-the-projects-hosts-out-of-the-path).

## Стек соединения {#the-connection-stack}

Все роли узлов и мобильные приложения используют один и тот же транспорт, [libp2p-camouflage-transport](https://github.com/Warp-net/libp2p-camouflage-transport/tree/v0.0.3) (v0.0.3), и одни и те же слои поверх него ([`core/warpnet/options.go`](https://github.com/Warp-net/warpnet/blob/main/core/warpnet/options.go)):

```text
application streams     Warpnet routes (/private/..., /public/...)
yamux                   stream multiplexing
Noise XX                encryption and peer authentication   <- the security layer
pnet (PSK, XSalsa20)    network and major-version separator, NOT a secret
TLS camouflage (uTLS)   looks like Chrome talking to www.googleapis.com, NOT verified
TCP                     IPv4 and IPv6; the server name is split across two writes
```

TCP — единственный транспорт; соединения через relay идут внутри него. Приватные сети libp2p не работают поверх QUIC и WebRTC.

### TLS-камуфляж {#tls-camouflage}

Его единственная задача — проходить через сети, которые блокируют неизвестные протоколы с помощью глубокой инспекции пакетов (DPI). Это не слой безопасности.

- **Инициатор соединения.** Отправляет TLS ClientHello с отпечатком Chrome (uTLS `HelloChrome_Auto`), SNI `www.googleapis.com` и ALPN `h2` и `http/1.1`. В пределах первых 2048 байт соединения запись, которая содержит имя сервера, разрезается на две посередине имени.
- **Принимающая сторона** (member, relay, модератор). Отвечает через `crypto/tls` из Go (TLS 1.2 или новее) и цепочку сертификатов, сгенерированную при запуске: конечный сертификат для `www.googleapis.com`, подписанный одноразовым CA с именем «Cloudflare Inc ECC CA-3». Этому CA никто не доверяет; он нужен только для того, чтобы рукопожатие выглядело правдоподобно. TLS-рукопожатие должно завершиться за 10 секунд. Одновременно идет не больше 64 рукопожатий; соединение, которое ждет свободного места дольше 30 секунд, закрывается.
- **Без проверки сертификата.** Инициатор соединения не проверяет сертификат. Вместо этого пир аутентифицируется через Noise внутри туннеля.
- **В Google и Cloudflare ничего не уходит.** TCP-соединение идет на IP-адрес пира. Поэтому монитор трафика вроде PCAPdroid показывает `www.googleapis.com` рядом с адресом вашего узла или relay-узла.

### Сетевой ключ (PSK) публичен {#the-pre-shared-key-is-public}

Режиму приватной сети в libp2p нужен 32-байтный ключ. Warpnet выводит его как `SHA-256(network name + major version)` ([`security/psk.go`](https://github.com/Warp-net/warpnet/blob/main/security/psk.go)): `SHA-256("warpnet0")` для всех релизов 0.x в `warpnet` (имя `mainnet` сначала заменяется на `warpnet`), `SHA-256("testnet0")` в `testnet`. Вычислить его может кто угодно. QR-код сопряжения содержит его, а relay-узел, запущенный с `--node.print-psk`, пишет его в лог.

Его назначение — разделение, а не секретность. Узел из другой сети или другой мажорной версии отваливается на первых же байтах, вместо того чтобы говорить на протоколе, которого не понимает. Поэтому релиз с новой мажорной версией меняет ключ. См. [Протокол](protocol.md#versioning-and-compatibility). Не рассчитывайте на него для конфиденциальности.

### Noise {#noise}

Noise (`Noise_XX_25519_ChaChaPoly_SHA256`, из go-libp2p) шифрует и аутентифицирует каждое соединение с помощью ключей идентичности Ed25519 обоих пиров. Инициатор знает, какой peer ID он ожидает (мобильное приложение берет его из QR-кода сопряжения), и рукопожатие проваливается, если другая сторона не может доказать эту идентичность. Именно это защищает содержимое, в том числе на соединениях через relay.

На member-узлах черный список пиров проверяется на шаге Noise: подключения к заблокированному пиру отклоняются до рукопожатия, входящие соединения — как только рукопожатие раскрывает peer ID ([`core/warpnet/noise.go`](https://github.com/Warp-net/warpnet/blob/main/core/warpnet/noise.go)).

Поверх Noise узел принимает запрос, только если он свежий и подписан ключом, который стоит за peer ID соединения. Приватные маршруты узел обслуживает только себе и устройствам, зарегистрированным при сопряжении; исключение — сам маршрут сопряжения ([`core/middleware/auth.go`](https://github.com/Warp-net/warpnet/blob/main/core/middleware/auth.go)). См. [Протокол](protocol.md#signing).

### yamux и лимиты соединений {#yamux-and-connection-limits}

Потоки мультиплексируются через yamux с keep-alive 15 секунд и тайм-аутом записи 30 секунд ([`core/node/node.go`](https://github.com/Warp-net/warpnet/blob/main/core/node/node.go)). Менеджер ресурсов libp2p ограничивает число соединений на один IPv4-адрес и на IPv6-префиксы /56 и /48, а также ограничивает частоту новых соединений из одной подсети. Менеджер соединений по умолчанию держит от 20 до 50 соединений; см. [Обнаружение](discovery.md#peer-prioritisation).

## Что делает member-узел {#what-a-member-node-does}

| Действие | Подробности | Код |
|---|---|---|
| Прослушивание | TCP 4001 на всех интерфейсах IPv4 и IPv6. Сетевые настройки узла имеют приоритет над `--node.port`, `--node.host.v4` и `--node.host.v6` | [`cmd/node/member/node/member-node.go`](https://github.com/Warp-net/warpnet/blob/main/cmd/node/member/node/member-node.go) |
| Проброс портов | Запрашивает у роутера проброс через UPnP или NAT-PMP | `libp2p.NATPortMap` |
| Достижимость | Выясняет через AutoNAT, доступен ли он извне, и отвечает на проверки AutoNAT для других | `libp2p.EnableAutoNATv2`, `EnableNATService` |
| Relay-клиент | Если узел недоступен извне, резервирует слот на relay-узлах из своего списка bootstrap-узлов (circuit relay v2, AutoRelay со списком bootstrap-узлов в роли статических relay) и анонсирует через них адреса `/p2p-circuit` | `warpnet.EnableAutoRelayWithStaticRelays` |
| Hole punching | Пытается перевести соединения через relay в прямые с помощью DCUtR, где это позволяют NAT, и пишет результат в лог | [`core/holepunch`](https://github.com/Warp-net/warpnet/tree/main/core/holepunch) |
| Relay-сервис | Запускает сервис circuit relay v2 с лимитами, приведенными ниже. Другие узлы резервируют на нем слоты, только если он есть в их списке bootstrap-узлов | [`core/relay/relay.go`](https://github.com/Warp-net/warpnet/blob/main/core/relay/relay.go) |
| Обнаружение | Kademlia DHT под `/warpnet` или `/testnet`, mDNS в локальной сети, анонсы через gossip | [Обнаружение](discovery.md) |
| Контент | Обменивается публичным контентом через потоки и gossip | [Протокол](protocol.md) |

Relay-узлы и узлы-модераторы используют те же AutoNAT, проброс портов, AutoRelay, hole punching и relay-сервис. Relay-узел при запуске объявляет себя публично доступным, поэтому обслуживает резервации, не дожидаясь AutoNAT.

### Лимиты relay {#relay-limits}

Узлы всех ролей используют одну и ту же конфигурацию circuit relay v2 ([`core/warpnet/options.go`](https://github.com/Warp-net/warpnet/blob/main/core/warpnet/options.go)):

| Лимит | Значение |
|---|---|
| Длительность одного соединения через relay | 1 час |
| Объем данных на одно соединение через relay | 1 GiB |
| Срок жизни резервации | 1 час |
| Резервации | 128 всего, 8 на IP, 32 на ASN |
| Одновременные соединения через relay на один пир | 16 |

После неудачной резервации AutoRelay ждет 5 минут, прежде чем снова обратиться к тому же relay-узлу.

### Отказы в резервации relay {#relay-reservation-refusals}

Когда member-узел получает соединение через relay от пира из своего черного списка, он отклоняет соединение и сообщает об этом relay-узлу через `/public/post/relay/refuse/reservation/0.0.0`. После этого relay отказывается соединять этого пира с member-узлом в течение одного срока жизни резервации (1 час). Этот маршрут обслуживают только relay-узлы. Relay принимает такое сообщение только от пира, у которого есть на нем резервация, и хранит не более 256 отказов на каждого пира с резервацией ([`core/relay/reservation-refusals.go`](https://github.com/Warp-net/warpnet/blob/main/core/relay/reservation-refusals.go)).

### Другие исходящие соединения {#other-outgoing-connections}

Узел устанавливает несколько соединений за пределами сети Warpnet:

| Соединение | Когда | Можно ли отключить |
|---|---|---|
| Проверка релизов: API релизов `codeberg.org` и `api.github.com`. Если вышел более новый релиз — его список контрольных сумм и подпись, а после одобрения обновления и архив, по ссылкам на загрузку из релиза (GitHub) | Десктопный member-узел в Linux (amd64, arm64) и Windows (amd64), relay-узел и модератор в Linux amd64: через минуту после запуска, затем раз в час. Не выполняется в macOS, в Snap-пакете и в варианте remote (браузерная панель) | `--node.self-update=false` |
| API блокчейна (по умолчанию TronGrid: `api.trongrid.io` в `warpnet`, `nile.trongrid.io` в `testnet`) | Только при использовании кошелька или спонсорских постов — вами или пиром, который вам платит; локальный платежный движок запускается при первом использовании | `--wallet.endpoint` или настройки кошелька задают другой endpoint |
| SMTP-сервер | Только если вы включили уведомления по email и настроили сервер | Настройки уведомлений |
| `www.youtube-nocookie.com` (из интерфейса десктопного приложения или браузерной панели) | Только когда вы нажимаете воспроизведение ссылки YouTube в посте | До нажатия ничего не загружается |

## Панель удаленного узла {#the-remote-nodes-dashboard}

Вариант remote ([`cmd/node/member/remote-member.go`](https://github.com/Warp-net/warpnet/blob/main/cmd/node/member/remote-member.go)) запускает тот же member-узел без графического интерфейса и сам отдает веб-интерфейс: `/` отдает приложение, а через `/ws` идут все запросы. По умолчанию он слушает `0.0.0.0:4999` (`--node.server.host`, `--node.server.port`).

- Каждое соединение `/ws` начинается с рукопожатия Noise XX (`Noise_XX_25519_ChaChaPoly_SHA256`) между браузером и узлом. Статический ключ узла хранится в файле `ws-noise.key` рядом с каталогом базы данных, а его отпечаток узел выводит при запуске. Браузер закрепляет ключ при первом контакте и отказывается продолжать, если ключ изменился.
- Запросы со страницы другого сайта отклоняются (`Origin` должен совпадать с хостом).
- Вызывать маршруты могут только браузеры, чей ключ был зарегистрирован успешным входом на этом узле. Регистрация хранится в памяти до выхода из аккаунта или до остановки узла.
- Сама страница (HTML и JavaScript) отдается по обычному HTTP. В сети, которой вы не доверяете, привяжите панель к `127.0.0.1` и подключайтесь к ней через SSH-туннель или поставьте перед ней обратный прокси с TLS.

Формат сообщений: [WebSocket API](developer-guide/ws-API.md).

## Что делают мобильные приложения {#what-the-mobile-apps-do}

Приложения для Android и iOS запускают один и тот же libp2p-хост, который только устанавливает исходящие соединения ([`warpdroid/node/node.go`](https://github.com/Warp-net/warpnet/blob/main/warpdroid/node/node.go), [`warpfone/node/node.go`](https://github.com/Warp-net/warpnet/blob/main/warpfone/node/node.go)): без слушающих сокетов, с тем же камуфляжным транспортом, PSK, Noise и yamux, с клиентом circuit relay и клиентом DHT. Их user agent — `warpdroid` и `warpfone`. Запросы они отправляют только сопряженному узлу.

1. **Запуск.** Приложение подключается к каждому bootstrap-адресу, который ваш узел передал ему при сопряжении, и обновляет свою таблицу маршрутизации DHT. При этом DHT-запросы уходят на bootstrap-узлы и, возможно, на другие публично доступные узлы Warpnet — независимо от того, находится ли ваш узел в локальной сети.
2. **Подключение к вашему узлу.** Приложение подключается к адресам, которые сообщил ваш узел: сначала к приватным (локальная сеть), к остальным — через 250 ms, к адресам relay — в последнюю очередь (стандартное ранжирование libp2p откладывает их еще на 500 ms, если есть публичный адрес). Используется первое установленное соединение.
3. **Сессия через relay.** Когда отвечает только адрес relay, сессия идет по цепочке телефон — relay — узел: это поток внутри камуфлированного соединения телефона с relay, со своим сквозным рукопожатием Noise между телефоном и узлом. Приложение не делает hole punching. Ваш узел пробует DCUtR на входящем соединении через relay, но у приложения нет адресов для прослушивания и обработчика DCUtR, поэтому узел пишет в лог `holepunch: protocol error`. Сессия через relay остается такой до следующего переподключения, и к ней применяются лимиты relay, описанные выше.

## Кто что видит {#who-sees-what}

| Наблюдатель | Видит | Не видит |
|---|---|---|
| Ваш провайдер, Wi-Fi или мобильная сеть | IP-адреса и порты, время и объем трафика, TLS ClientHello для `www.googleapis.com` | peer ID, маршруты, содержимое |
| Bootstrap- или relay-узел (трафик DHT) | ваш IP-адрес, peer ID и публичный ключ, user agent мобильных приложений, ваши DHT-запросы | содержимое ваших потоков с другими узлами |
| Relay-узел (сессия через relay) | оба IP-адреса и peer ID, время и объем трафика | содержимое: он пересылает шифротекст Noise |
| Любой узел Warpnet | ваши адреса и до 10 пиров, к которым вы подключены (gossip-анонсы); информацию о вашем узле (`/public/get/info`: ID пользователя-владельца, версию, время запуска, адреса, доступность, peer ID сопряженных устройств); ваш публичный профиль и публичные посты; запросы, которые вы ему отправляете | ваши приватные данные и приватные маршруты |
| Шлюз моста, которым вы пользуетесь | то, что ваш узел ему отправляет, включая ваш ключ моста; см. [Мосты](bridge.md#privacy-and-trust) | все, что ваш узел ему не отправляет |
| Ваш собственный узел | все, что делают приложения и панель | |

Публичный контент публичен по замыслу: все, что возвращает публичный маршрут, может получить любой узел сети. О том, что шифруется при хранении и как устроены идентичности, см. [Безопасность](security.md).

## Как обойтись без хостов проекта {#keeping-the-projects-hosts-out-of-the-path}

1. Запустите собственный relay-узел (`cmd/node/relay`, файл релиза `relay_linux_amd64.tar.gz`) на хосте с публичным IP.
2. Задайте ему секретный `--node.seed`. Ключ relay-узла выводится из этого значения; без него — из имени сети, каталога базы данных, IPv4-хоста и порта, которые легко угадать.
3. Запустите его также с `--node.bootstrap`. Иначе он возьмет встроенный список и подключится к relay-узлам проекта.
4. Укажите адрес своего relay-узла в списке bootstrap-узлов своего member-узла: на экране **Settings** или через `--node.bootstrap`.

После этого member-узел начинает DHT с вашего relay-узла, резервирует слоты relay только на нем и передает тот же список телефону при сопряжении. При этом он по-прежнему подключается к узлам, которые находит через DHT, gossip или mDNS, — в том числе к relay-узлам проекта, если их анонсирует какой-нибудь узел, с которым он общается.
